## Format

Each applied rule is one query param, `field__operator=value`:

```txt
/orders?status__eq=paid&amount__between=10,50&tags__in=urgent,vip&deletedAt__isEmpty
```

- The key is the field name and the operator id, joined by `__`. Field names may contain `__` too: the key is split at the last one.
- Ranges and lists are comma-separated. A comma inside a list item is written `%252C` (`%2C`, escaped once more), so it isn't taken as a separator.
- Operators without a value write the bare key, e.g. `deletedAt__isEmpty`.
- Values are already normalized: numbers are numbers, booleans are `true`/`false`, dates are `YYYY-MM-DD`.
- An OR adds `join=or`. AND is the default and adds nothing.
- Two rules on the same field and operator repeat the key: `status__ne=draft&status__ne=void`.
- Rule ids are not stored.

Only what a URL can't hold is escaped: spaces, `&`, `=`, `#`, `+`, `%` and non-ASCII (which address bars show decoded). `,` `:` `/` `@` `$` `[` `]` stay as they are.

Other params (`page`, `sort`…) are left alone. When a filter is applied, every param that belongs to the filter is replaced: `join`, and any `field__…` key whose field is declared, including rules that were dropped as invalid.

### Encoding and decoding

The provider does this for you. Outside React (a backend, a script, a test) use the core functions:

```ts
import { decodeFilters, encodeFilters } from "@querycn/filter-core"

const context = { fields: orderFields }

encodeFilters(
  {
    join: "and",
    rules: [
      { id: "a", field: "status", operator: "eq", value: "paid" },
      { id: "b", field: "amount", operator: "between", value: ["10", "50"] },
      { id: "c", field: "customer", operator: "contains", value: "" }, // incomplete
    ],
  },
  context
)
// → "status__eq=paid&amount__between=10,50"

decodeFilters(new URL(request.url).searchParams, context)
// → { join: "and", rules: [{ id: "u0", field: "status", … }, { id: "u1", … }] }
```

`decodeFilters` takes a query string (with or without `?`) or a `URLSearchParams`. It never throws. A URL is user input, so:

- params that aren't `field__operator` keys of a declared field are ignored;
- each rule is checked on its own, and rules with an unknown field, an operator the field doesn't offer, or a value of the wrong shape are dropped (see [complete rules](/docs/filter/operators#complete-rules));
- `null` or an empty string gives an empty filter.

```ts
decodeFilters("status__eq=paid&nope__eq=1&amount__between=1&page=2", context)
// → { join: "and", rules: [{ id: "u0", field: "status", operator: "eq", value: "paid" }] }
```

Decoded rules get positional ids: `u0`, `u1`, and so on. The server and the client decode the same URL to the same state, so server-rendered markup matches after hydration.

### Custom format

To match a URL scheme you already have, pass a `urlFormat` to the provider, and the same one to `decodeFilters`/`parseFilters` on the server. A format maps one rule to one param and back. This one writes `_name=["like","%acme%"]`:

```ts
import type { UrlFormat } from "@querycn/filter-core"

const toUrlOperator: Record<string, string> = { contains: "like", eq: "eq", in: "in" }
const fromUrlOperator = Object.fromEntries(
  Object.entries(toUrlOperator).map(([ours, theirs]) => [theirs, ours])
)

export const legacyUrlFormat: UrlFormat = {
  encodeRule: ({ field, operator, value }) => [
    `_${field}`,
    JSON.stringify(
      operator === "contains"
        ? ["like", `%${value}%`]
        : [toUrlOperator[operator] ?? operator, value]
    ),
  ],
  decodeRule: (key, value) => {
    if (!key.startsWith("_")) return null // not a filter param
    const [operator, raw] = JSON.parse(value) // a throw drops the param
    return {
      field: key.slice(1),
      operator: fromUrlOperator[operator] ?? operator,
      value: operator === "like" ? String(raw).replace(/^%|%$/g, "") : raw,
    }
  },
  joinParam: "_join",
}
```

```tsx
<FilterProvider fields={orderFields} adapter={adapter} urlFormat={legacyUrlFormat} />

parseFilters(await props.searchParams, { fields: orderFields, urlFormat: legacyUrlFormat })
```

- `encodeRule` gets complete, normalized rules only. `value` is `null` for operators without one, an array for ranges and lists.
- `decodeRule` returns `null` for params that aren't rules, e.g. `page`. The rule it returns is validated like any other, so raw text is fine: `"5"` becomes `5` on a number field.
- A param belongs to the filter when `decodeRule` returns a rule for a declared field. Those are the params an apply replaces. A param `decodeRule` throws on is left alone.
- An OR is written as `joinParam=or` (default `join`).

## Adapters

An adapter tells `FilterProvider` where the applied filter lives. Pass one as `adapter`:

| Adapter | Import | Use it for |
| --- | --- | --- |
| memory (default) | built in | Filters that shouldn't touch the URL: dialogs, tests. |
| `useBrowserUrlAdapter()` | `@querycn/filter-react` | Plain React and Vite apps without a client router. |
| `useReactRouterAdapter()` | `@querycn/filter-react/react-router` | react-router 6.4+ and 7. |
| `useNextAdapter()` | `@querycn/filter-next` | Next.js App Router (or `<NextFilterProvider>`). |
| `createMemoryAdapter(initial?)` | `@querycn/filter-react` | Memory with a starting query string, e.g. `"status__eq=paid"`. It has no `readServer`, so on server-rendered pages seed it only with values the server knows too. |

All URL adapters:

- **replace** the current history entry instead of pushing a new one, so applying a filter ten times doesn't add ten Back steps;
- keep the path, the hash and the other query params. Those are rewritten with the same light escaping, e.g. `a%2Cb` becomes `a,b`; their values don't change.

Two filters on one page share the query string, so give them different field names.

The browser adapter only sees the URL in the browser. During server rendering and hydration it reports an empty filter, then the real one right after. The Next.js and react-router adapters read the URL through the router, so their server render already has the filter.

### Changing other params on apply

`onApply` runs when applying changes the filter. The params it returns are written in the same navigation. The usual case is going back to the first page:

```tsx
<FilterProvider
  fields={orderFields}
  adapter={adapter}
  onApply={() => ({ page: null })} // null removes the param
/>
```

It receives the new applied state, in case the params depend on it.

### Custom adapters

An adapter is a small object holding a query string. This one keeps the filter in `localStorage`, applying each patch with `applyParamChanges`:

```ts
import { applyParamChanges, type UrlStateAdapter } from "@querycn/filter-react"

export function createStorageAdapter(key: string): UrlStateAdapter {
  const listeners = new Set<() => void>()
  const read = () => localStorage.getItem(key) ?? ""
  return {
    read,
    write: (changes) => {
      const next = applyParamChanges(read(), changes)
      if (next === null) return // nothing changed
      localStorage.setItem(key, next)
      listeners.forEach((listener) => listener())
    },
    subscribe: (onChange) => {
      // `storage` fires for changes made in other tabs
      const onStorage = (event: StorageEvent) => event.key === key && onChange()
      listeners.add(onChange)
      window.addEventListener("storage", onStorage)
      return () => {
        listeners.delete(onChange)
        window.removeEventListener("storage", onStorage)
      }
    },
    readServer: () => "",
  }
}
```

Create it once (module scope or `useState(() => …)`), not on every render.

## Router notes

- **react-router + `<ScrollRestoration>`**: if the URL has a hash, every apply scrolls to its target, because react-router scrolls to the hash before checking `preventScrollReset`. Use `getKey` based on the pathname, or avoid hashes on filtered pages.
- **react-router + `useBlocker`**: when a blocker stops the navigation, the value just written waits until the URL changes again.
- **Next.js**: see [Next.js](/docs/filter/nextjs) for `shallow`, `<Suspense>` and `basePath`.
